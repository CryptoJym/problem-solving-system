# Ordered Problem-Solving Skill System

This ranking is based on how much each skill prevents wasted effort, how often it appears across the source material, and how early it changes the quality of downstream work. The 2026-05-12 research update keeps the original nine public IDs stable, adds one adoption-design skill, and recommends a slightly different teaching sequence: generate options before narrowing them, then design adoption before operating rhythm.

## Practical Sequence

Use this sequence for a real problem:

1. **Name the current frame.** Write the problem as currently understood, then rewrite it three ways: goal frame, system frame, and user/operator frame.
2. **Collect symptoms before causes.** Prohibit solutions while gathering observations, UDEs, and stakeholder accounts.
3. **Select the problem.** Compare candidate problems by value, feasibility, control, time horizon, and evidence strength.
4. **Build the causal model.** Use 5 Whys, CRT, fishbone, and Theory of Constraints. Keep cause statements testable.
5. **Generate options independently.** Brainwrite before group discussion; vote only after options have been expanded, analogized, and combined.
6. **Expose decision traps.** Ask where the team is treating a choice as yes/no, seeking confirming evidence, ignoring base rates, or arguing from personal domain bias.
7. **Reality-test assumptions.** Get base rates, interview experts for patterns, seek disagreement, and inspect the system directly.
8. **Prototype the riskiest assumption.** Use the cheapest artifact that can teach something real: sketch, script, huddle, policy draft, checklist, simulation, MVP, PDSA cycle, or live pilot.
9. **Design adoption.** Check stakeholder fit, barriers, champions, feedback paths, adoption outcomes, and fidelity before rollout.
10. **Implement the smallest operating rhythm.** Convert the adopted solution into recurring behavior, visible metrics, accountability, standard work, and feedback.
11. **Close the learning loop.** Record what failed, what changed, what evidence moved, which system update was made, and who owns the review.

## What To Avoid

- Jumping from symptom to solution.
- Letting the loudest person set the frame.
- Treating a 5 Whys chain as valid without evidence and if-then logic.
- Brainstorming with unprepared people.
- Choosing one option before asking what would happen if that option vanished.
- Overbuilding a prototype before the riskiest assumption is clear.
- Treating adoption as a communication task instead of a context-fit and behavior-change task.
- Calling work done without observable behavior change or evidence.
